# Домены, сервер и границы клиентского проекта

Основной адрес клиентов: **https://cloud.mshostcloud.org**. Панель MSHost/MCSManager:
https://game.mshostcloud.org, демон — `wss://game.mshostcloud.org:443/daemon/`.
Домен в клиенте предложен по умолчанию и остаётся редактируемым.
Уже добавленные аккаунты автоматически на другой адрес не переводятся.

## Что произошло при переходе с DuckDNS 28 октября 2026

DNS Cloudflare был настроен в режиме DNS only. Caddy остался внешним reverse proxy,
облако — на существующей Ubuntu VM с Nextcloud AIO. Данные и сервер не переносились заново.

Первоначально HTTP-01/TLS-ALPN проверки сертификатов не проходили из-за входящего
сетевого доступа. Установлена сборка Caddy 2.11.7 с модулем `dns.providers.cloudflare`;
сертификаты получены через DNS-01. Токен ограничен одной зоной с правами Zone Read / DNS Edit,
хранится в защищённом локальном envfile и не публикуется вместе с исходниками.
DNS only для игрового имени нужен, поскольку обычный HTTP-прокси Cloudflare не проксирует Minecraft TCP.

Автоматический административный скрипт AIO сначала получил HTTP 403:
потребовались Fetch Metadata и штатная административная сессия. После исправления
вход дал HTTP 201; загрузка страницы с проверкой обновлений оказалась медленной.
Для API использовались CSRF-токены той же сессии.

После остановки дочерних контейнеров и изменения домена был перезапущен mastercontainer.
Это выявило отдельную сетевую проблему: NAT-интерфейс VM ранее потерял IPv4 DHCP-аренду,
исходящий маршрут и DNS. Mastercontainer не мог достичь ghcr.io и не поднимал интерфейс AIO.
Переподключение NAT-адаптера восстановило DHCP. Host-only SSH сохранился; VPN не отключали.

Ранний отчёт «Completed» проверил installed/maintenance слишком рано:
приложение ещё содержало старые trusted_domains и overwrite.cli.url.
Поэтому он не был принят как подтверждение переноса.
Пользователь завершил работу через штатные Stop containers / Start containers в AIO.
Домен в AIO, NC_DOMAIN контейнера, trusted_domains и overwrite.cli.url должны согласоваться;
доступность одного status.php этого не доказывает.
Для штатного способа смены домена перезапуск mastercontainer не требуется.

Пользователь также настроил точечный маршрут Windows к публичному IP сервера и исключения
приложений AdGuard VPN. Это два независимых механизма; маршрут к серверному IP
сам по себе не задаёт обратный путь Caddy ко всем внешним посетителям.
Обычный интернет-трафик продолжал идти через VPN.

В последующей ручной правке Caddyfile старый игровой домен оказался объявлен дважды.
Caddy отверг файл как ambiguous site definition. Подготовленный кандидат прошёл validate;
пользователь применил исправление и запустил службу вручную.
После этого подтверждены Running, совпадение файла с активной конфигурацией,
HTTPS облака и панели и заданные 302-редиректы со старых адресов.
Для WebDAV/API, где требуется сохранить HTTP-метод, следует отдельно оценить 307/308.
Редирект не заменяет проверку существующих авторизованных клиентов.

## Что не хранится в этих форках

Здесь нет рабочей конфигурации сервера, реальных SSH-ключей, паролей, API-токенов,
Android signing keystore, клиентских профилей, sync.db или пользовательских файлов.
Скрипты VM и локальные административные отчёты находятся отдельно от клиентского исходного кода.
Не запускайте первоначальные сценарии установки/восстановления AIO ради смены домена.

Источники: [смена домена AIO](https://github.com/nextcloud/all-in-one#how-to-change-the-domain),
[Cloudflare-модуль Caddy](https://github.com/caddy-dns/cloudflare),
[DNS only для не-HTTP сервисов](https://developers.cloudflare.com/dns/proxy-status/use-cases/).

## 29 октября: TOTP и часы виртуальной машины

Пользователь сообщил, что старые TOTP-коды не принимаются, а подтверждение нового
секрета после генерации QR бесконечно ожидает. Проверка показала отставание системных
часов VM более чем на восемь часов. Windows и независимый внешний источник согласовались;
три NTP-сервера независимо подтвердили примерно +29 476 секунд относительно VM.

Chrony был запущен и имел выбранный источник, но System time показывал примерно
29 445 секунд slow of NTP time. Небольшой Last offset и Leap status Normal относятся
к NTP-часам chrony и сами по себе не доказывают правильность системных часов.
При стандартном makestep 1 3 большой сдвиг после начальных обновлений может
исправляться плавно очень долго.

С паролем sudo, введённым локально и не сохранённым, выполнены online,
ограниченный makestep 0.5 3, burst 4/4 и makestep. Существующие TOTP-секреты,
настройки аккаунтов, файлы chrony и VPN не менялись. После исправления независимая
проверка показала около 0,0014 секунды расхождения, дата в контейнере Nextcloud согласовалась.
На первой пробе timedatectl ещё сообщал NTPSynchronized=no. Через две минуты
повторная независимая проверка дала около 0,008 секунды, а NTPSynchronized стал yes.

После исправления времени пользователь подтвердил, что TOTP снова работает. После длительной паузы/возобновления
VM следует проверять именно системное время и System time в chronyc tracking.
Не нужно сбрасывать или отключать 2FA ради исправления часов.
